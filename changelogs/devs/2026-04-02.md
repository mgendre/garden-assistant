### Backend

- **Entity** : ajout de `ParentPlantId` (Guid?, self-referencing FK) sur l'entité `Plant` avec migration EF Core. Relation `Parent` / `Varieties` configurée en Fluent API (US-306)
- **PlantSeeder** : seeding en deux passes — les espèces parentes d'abord, puis les variétés via le champ `parentKey` dans les fichiers JSON (US-307)
- **Seed data** : 27+ variétés ajoutées sur 17 espèces parentes (tomate, courge, haricot, basilic, pois, laitue, fraisier, framboisier, poivron, piment, chou, radis, fenouil, concombre, tournesol). Restructuration complète du haricot : fusion haricot-nain/haricot-à-rames en un parent unique avec 10 variétés (filet nain/rames, coco nain/rames, flageolet, à écosser). Ajout du haricot d'Espagne (P. coccineus) et de la courge musquée comme nouvelles espèces (US-308, US-308a, US-308b)
- **Associations courge musquée** : copie des 10 associations de `courge` vers `courge-musquee` dans `associations.json` pour que C. moschata hérite des mêmes compagnonnages que C. pepo (US-308)
- **Framboisier** : renommage de `framboisier-remontant` en `framboisier-d-automne` (clé et nom affiché)
- **Calendriers variété** : actions spécifiques par variété (tomate-naine sans taille, framboisier-d-automne, radis-d-hiver, courge-musquee, haricot-à-écosser). Héritage des actions du parent quand la variété n'en définit pas (US-308)
- **PlantService** : heritage des proprietes (`WaterNeeds`, `SunRequirement`, `SoilType`, `RootDepth`, `GrowthHabit`, `Lifecycle`, famille, genre) et des mecanismes (`PlantMechanisms`) du parent vers la variete. Heritage de `HarvestReadiness` et des actions calendrier (US-309)
- **PlantAssociationService** : resolution transparente des varietes vers leur parent pour le scoring d'associations. Les DTOs retournent les IDs de varietes d'origine mais affichent l'espece parente dans les details (US-310)
- **Validation seed data** : tests xUnit verifiant les enums (`SunRequirement`, `SoilType`, etc.) dans tous les fichiers JSON de seed. Correction de valeurs invalides detectees (US-308)

### Frontend

- **NSwag** : client TypeScript regenere avec les champs `parentPlantId`, `parentPlantKey`, `isVariety` sur `PlantDto` (US-311)
- **My-plants redesign** : remplacement des `<app-plant-card>` depliables par une liste compacte `.plant-item` (emoji + nom + badge famille). Ajout d'un `<app-search-input>` pour filtrer par nom, nom latin ou famille via un signal `searchQuery` et un `computed` `filteredPlants`. Clic sur un item ouvre `PlantDialogService.openDetail()`, bouton supprimer via `MyPlantsStore.toggle()`. Le composant injecte desormais `CompanionStore` (pour `getPlantEmoji` / `getFamilyClass`) en plus de `MyPlantsStore`
- **Plant detail dialog** : correction du double padding, du padding-top excessif, et suppression de la bordure/ombre sur les plant-cards a l'interieur du dialog (`.plant-detail-dialog .plant-card { box-shadow: none; border: none }`)
- **Association panels** : suppression de la bordure/ombre sur les plant-cards a l'interieur des panels d'association pour eviter la double bordure

### Infrastructure

- Aucun changement d'infrastructure dans cette branche

### Points d'attention

- L'heritage de proprietes se fait au niveau service (pas en BDD) : une variete sans valeur propre recoit celle de son parent au runtime
- Les associations d'une variete sont resolues via le `ParentPlantId` — aucune association n'est stockee directement sur les varietes
- Le seeding deux passes impose que les fichiers JSON de varietes referent un `parentKey` correspondant au `Key` d'une espece existante
- Les tests de validation des seed data (`SeedDataValidationTests`) sont a maintenir lors de l'ajout de nouvelles plantes ou varietes
- Le backlog E20 n'est pas encore marque comme termine — a mettre a jour apres merge
